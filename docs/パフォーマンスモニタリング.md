# 社内図書貸出管理システム パフォーマンスモニタリング

| 項目 | 内容 |
|------|------|
| 対象 | 開発担当・運用担当 |
| 最終更新 | 2026年9月 |

**New Relic、Prometheus、Grafana、Datadog APM は使わない。** リクエストのトレースやレイテンシのダッシュボードは無い。死活は `/up` と画面確認、遅さの調査は OS と Web サーバーログである。例外は [エラートラッキング](./エラートラッキング.md)。ログの置き場は [ログ管理](./ログ管理.md)。

性能の目標値は [基本設計書 10-1](./基本設計書.md)（画面 3 秒、同時 ~50、ISBN タイムアウト 5 秒）。自動で計測してアラートする仕組みは無い。

---

## 1. 何を使うか

| 環境 | やり方 |
|------|--------|
| **本サーバー** | ログイン画面と `/up`（[保守運用手順書 第4章](./保守運用手順書.md)）。CloudWatch Logs。必要なら ECS タスクと RDS の状態 |

Laravel のヘルスチェックは `bootstrap/app.php` の `health: '/up'`。アプリが応答すれば `200`。DB や外部 API（OpenBD 等）の遅さはここだけでは分からない。社外から `/up` を見て Slack する製品（例: Uptime Robot）は **未導入**（[障害予防の3点](./障害予防の3点.md)）。

Composer の `laravel/pail` はログの追従であり、APM ではない。Telescope / Pulse / Horizon は入っていない。

## 3. 遅いときの見方

| 症状 | まず見るもの |
|------|----------------|
| 画面全体が開かない | `/up`、ALB、Fargate、RDS（[保守運用手順書 第4章](./保守運用手順書.md)） |
| 特定画面だけ遅い | CloudWatch Logs。ISBN 登録は外部 API（最大約 5 秒） |
| ディスク不足 | RDS ストレージ、CloudWatch のログ量（[保守運用手順書 第9章](./保守運用手順書.md)） |

本番で `APP_DEBUG=true` にしない。デバッグ表示は応答を遅くし、内部情報も出す。
