# 社内図書貸出管理システム ドキュメントの管理場所と最新化

| 項目 | 内容 |
|------|------|
| 対象 | 開発担当・運用担当 |
| 最終更新 | 2026年9月28日 |

**正本は Git リポジトリの `docs/` である。** Notion、Confluence、Google ドキュメント、印刷物を正にしない。コードと食い違ったら `docs/` を直す。仕様と設計のどれを見るかは [システム仕様書と設計書](./システム仕様書と設計書.md)。ファイル名の一覧の目安は [基本設計書 付録 B](./基本設計書.md)。

---

## 1. 置き場

| もの | 場所 |
|------|------|
| リポジトリの入口 | ルートの [README.md](../README.md)（`docs/` への案内） |
| 設計・手順・運用 | リポジトリ直下の `docs/*.md` |
| AWS 定義 | `infra/` と [AWSセットアップ](./AWSセットアップ.md)（本サーバー。未デプロイ） |
| 構成図 | `docs/system-architecture.drawio` |
| ER 図 | [基本設計書 第5章](./基本設計書.md) |
| AWS の手順 | [AWSセットアップ](./AWSセットアップ.md) |
| ライブラリの README | `vendor/` / `node_modules/`（このシステムの手順ではない） |

リンクは相対パス（`./マニュアル.md`）にする。Wiki へコピーする場合は、コピー側を正にしない。

パスワード、`APP_KEY`、Webhook URL は資料に書かない（[シークレット管理](./シークレット管理.md)）。

---

## 2. いつ直すか

決まった月次のドキュメント棚卸はない。**挙動や手順が変わったとき** に直す。

| きっかけ | 直す資料の例 |
|----------|----------------|
| 画面・権限・貸出の仕様 | マニュアル、基本設計、詳細設計、主要機能一覧 |
| `.env` / 外部 API | 環境変数とシークレット、外部サービスAPI |
| サーバー作業（cron、dump、反映） | 保守運用手順書、定期メンテナンス、データバックアップリストア、障害予防の3点 |
| 新資料を追加した | [基本設計書 付録 B](./基本設計書.md) と、関連資料の相互リンク。入口が変わるなら [README.md](../README.md) |

コードと同じコミット（または直後のコミット）で直す。本サーバーへはイメージ更新で届く。

---

## 3. 直し方

1. 該当する Markdown / drawio を編集する
2. 冒頭の **最終更新** と末尾の **改訂履歴** を付ける（日付と、何が変わったか 1 行）
3. 同じ内容を複数ファイルに長く書かない。手順の正は 1 か所、他はリンク
4. 古いファイル名は残さない

---
