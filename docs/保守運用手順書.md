## 4. 死活確認

1. ブラウザでシステムの URL を開く
2. ログイン画面が出ること
3. 管理者または一般でログインできること
4. （任意）ヘルスチェック

```bash
curl -fsS -o /dev/null -w "%{http_code}\n" https://本サーバーのURL/up
```

プロセスは ECS タスクと RDS の状態で見る。`systemctl` で OS に入る手順は本サーバーでは使わない。

## 5. cron と Slack 通知

期限切れ Slack は、画面ではなく **コンテナ内の毎分 `schedule:run`** が動かします。スケジュール定義は `routes/console.php` です（毎分、タイムゾーン `Asia/Tokyo`）。OS の cron は使わない（[AWSセットアップ](./AWSセットアップ.md)）。

### 5-1. スケジュール

Fargate コンテナ内で毎分走る。未デプロイのあいだは届かない。確認は ECS Exec またはワンショットタスクから `php artisan schedule:list`。

未起動だと、期限切れになっても Slack に届きません。

### 5-2. 通知の内容

| 宛先 | 条件 |
|------|------|
| 管理チャンネル | Secrets Manager / タスク環境の `SLACK_OVERDUE_WEBHOOK_URL` |
| 一般利用者への DM | `SLACK_BOT_TOKEN`。図書システムのメールと Slack のメールが一致すること |
| 管理者本人への DM | 送らない |

同じ貸出は `loans.slack_notified_at` が入ると再送しません。件数 0 のときは送りません。1 分間デモも対象です。

### 5-3. 手動確認

```bash
# 送らず件数と内容だけ見る
php artisan library:notify-overdue-slack --dry-run

# 実験メッセージをチャンネルへ
php artisan library:notify-overdue-slack --sample

# 実験 DM（メールは Slack と一致させる）
php artisan library:notify-overdue-slack --sample --to=user@example.com
```

## 6. バックアップと復元

詳細手順は [データバックアップリストア.md](./データバックアップリストア.md) です。本番 DB は MySQL です。バックアップなしの直接編集はしません。

要点:

- 毎日 `mysqldump` → gzip。表紙は `cover_images` に含まれる
- 復元は計画停止のうえ `gunzip | mysql`
- アプリ更新の直前にも取る（[第8章](#8-アプリの更新)）

## 7. 設定変更

設定は Secrets Manager と ECS タスク定義です。Git とイメージに実値を入れません。項目の正本は [環境変数とシークレット](./環境変数とシークレット.md)、置き場は [環境変数とシークレット](./環境変数とシークレット.md) です。変更後はタスクを再起動する。

| 変数 | 用途 |
|------|------|
| `APP_URL` | Slack のリンク先。本番 URL と一致させる |
| `APP_DEBUG` | 本番は `false` |
| `LOG_CHANNEL` | **`stderr`**（CloudWatch へ出す） |
| `DB_*` | MySQL 接続 |
| `RETURN_LOCATION_RESTRICTED` | 場所制限 ON/OFF |
| `RETURN_ALLOWED_NETWORKS` | 許可 CIDR（カンマ区切り可） |
| `RETURN_LOCATION_NAME` | 画面に出す場所名 |
| `RETURN_ALLOW_LOCALHOST` | 本番は `false` |
| `SLACK_OVERDUE_WEBHOOK_URL` | 管理チャンネル |
| `SLACK_BOT_TOKEN` | 本人 DM |
| `MAIL_*` | パスワード再設定メール |
| `INITIAL_PASSWORD` | 新規利用者の初期パスワード |

場所制限の詳細は [マニュアル 6-1](./マニュアル.md#6-運用ルール) です。オフィスのグローバル IP が変わったら `RETURN_ALLOWED_NETWORKS` を当日中に更新します。

## 8. アプリの更新


1. DB をバックアップする（[データバックアップリストア](./データバックアップリストア.md)）
2. 作業内容と影響を管理者に伝える
3. イメージをビルドしてタスクを更新する（[AWSセットアップ](./AWSセットアップ.md)）。Linux 1 台への `git pull` は使わない
4. ログイン → 本棚または管理メニュー → 借りる／返すのどれかを確認する
5. フロント変更後はブラウザでスーパーリロード（`Cmd + Shift + R`）

チェックリストとロールバックは [バグ対応書 第7章・第8章](./バグ対応書.md) です。マイグレーションがある更新は、戻し方が難しいのでバックアップを必須にします。手順の整理は [スキーマ設計とマイグレーション.md](./スキーマ設計とマイグレーション.md) です。ダンプの取り方は [データバックアップリストア.md](./データバックアップリストア.md) です。資料の直し方は [ドキュメント管理.md](./ドキュメント管理.md) です。

## 9. ログとディスク


アプリログは CloudWatch Logs（`LOG_CHANNEL=stderr`）。コンテナのディスク上の `laravel.log` は本サーバーの正ではない。保持は 3 日の定義（[ログ管理](./ログ管理.md)）。

RDS のストレージと CloudWatch の取り込み量を見る。OS の `df -h` は使わない。

## 10. 利用者・蔵書の保守

サーバーに入らず、管理画面で行う作業です。

| 作業 | 手順の要点 |
|------|------------|
| 利用者追加 | 利用者登録（最大 5 名）。完了後に人ごとの仮パスワードが表示される。コピーして本人へ伝え、初回ログインで変更させる |
| パスワード忘れ | 管理者がリセットするか、本人がメール再設定（メールが届く設定であること） |
| 除名 | 貸出中がないこと。履歴も消える。[マニュアル](./マニュアル.md) |
| 資料追加 | ISBN 検索、または Excel 取り込み |
| 表紙なし | 全資料編集の手動設定、または「表紙がない本だけ再取得」 |
| 在庫追加 | 同じ ISBN を再登録、または Excel の冊数 |

管理者は本棚（`/dashboard`）を使いません。一般社員の見え方を確認するときは一般アカウントを使います。

## 11. 計画停止

migrate、DB 復元、タスク更新の前に行います。

1. 管理者・利用者へ開始時刻と終了見込みを連絡する
2. 新規の貸出・返却を控えてもらう
3. 作業する
4. 第4章の死活確認をする
5. 完了を連絡する

社内業務時間外を推奨します。24時間必須のサービスではありません（[基本設計書 10-2](./基本設計書.md)）。

## 12. よくある運用作業

症状から資料を探すときは [よくあるトラブル](./よくあるトラブル.md) です。

| やりたいこと | 手順 |
|--------------|------|
| 画面が古い | スーパーリロード。イメージに `npm run build` 済みか |
| 社外から借りられてしまう | `RETURN_LOCATION_RESTRICTED=true`、`RETURN_ALLOW_LOCALHOST=false`、CIDR |
| 社内なのに借りられない | 現在のグローバル IP が CIDR に入っているか |
| Slack が静か | コンテナ内の毎分、Webhook、期限切れ件数、`--dry-run` |
| メールが届かない | `MAIL_*`、CloudWatch Logs |
| ディスク不足 | RDS ストレージ、古いバックアップ削除（[データバックアップリストア](./データバックアップリストア.md)） |
| 設定が反映されない | Secrets を直してタスクを再起動 |
